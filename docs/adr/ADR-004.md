# ADR-004 — Idempotency Keys for transfers (storage and retention)

- Status: Accepted
- Date: 2026-11-06

## Context
A client sent a 300 transfer, lost the response and retried. Expected 700 / 300, got 400 / 600. The sum stayed 1,000: a replay is a valid transfer, so the conservation invariant can’t catch it.
The server needs to know when a request is a retry: the client sends an Idempotency-Key.
- A request without an Idempotency-Key header is rejected with 400
- The same idempotency key with the same request body should return the same code and response
- The same idempotency key and different request body should return 422
- Client retries happen within minutes; 24 h also covers a client that is down overnight. Documented in the API; a retry after 24 h creates a second transfer.


## Options
1. Server Memory-> Rejected: a crash/restart loses everything, not shared between two instances
2. Redis-> Rejected: No atomicity with the database: a crash between the Redis write and the database write leaves a debit without a key, or a key without a debit
3. A table within the database-> Accepted: Gives atomicity, ensures that the key and the transfer are committed or rolled back together. 




## Decision
- Idempotency keys are saved in a table within the database.
- Idempotency key and transfer are parts of the same transaction
- The row stores a SHA-256 of the request body and the response status and body, so a different body with the same key returns 422
- A business rejection (404, 422) is stored with the key, so a replay returns the same rejection even if the account was funded in between. A technical error rolls back everything, key included, so the client can retry.
- Concurrent requests with the same key are serialized by the unique index: INSERT … ON CONFLICT DO NOTHING waits for the first transaction, then returns 0 rows and the stored response. In 20 runs out of 20, ten concurrent requests with the same key all got 201, and the sender was debited once.
- Idempotency key Primary key (client_id, key), to be added in V5. Until authentication exists, client_id comes from a Client-Id header
- Keys are retained 24 h, as documented in the API contract.

## Consequences and trade offs
- A key is never committed without its outcome, and a transfer is never committed without its key
- 2 extra statements per transfer (INSERT, then UPDATE), about 0.6 ms: 2 × 0.29 ms per round trip, measured on 2026-11-04.
- Purge: an index on created_at and a batched DELETE (… WHERE created_at < now() - interval '24 hours',
  10,000 rows per batch) so the purge never holds long locks. Index to be added in V5.
- Partitioning by day is NOT used yet: in PostgreSQL a unique constraint on a partitioned table must
  include the partition column, so a retry just after midnight would miss the key and debit twice.
- About 15 GB at steady state for 50 M transfers a day (estimate: ~300 bytes per row with the index). Retention bounds the size.


## When to choose another option
- If the debit happens in another service, keep the key with my own state, publish through an outbox, and the other service deduplicates with its own key.
- A client needs more than 24 hours
- The batched DELETE can't keep up with 24 h of keys, or autovacuum falls behind on the table
  -> partition by day, and check yesterday's partition before inserting a key.
