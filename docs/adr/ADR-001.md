# ADR-001 — Concurrency control for transfers

- Status: Accepted
- Date: 2026-10-10

## Context
Kobo is a neo-bank application. Most accounts are cold, a few (merchants, fee accounts) are very hot.
Core invariants to be preserved are the following:
- The sum of the balances is constant
- There is no negative balance
A naive read-modify-write strategy broke the core invariants 5 times out of 5. So we need to find other options to preserve the core invariants.
Deadlocks, lost updates, and other concurrency issues should be avoided.


## Options
1. Naive -> Rejected: Core invariant broken 5 times out of 5
2. READ COMMITTED + SELECT … FOR UPDATE, locks acquired in ascending id order -> Accepted as fallback: Core invariant preserved (276 ms)
3. UPDATE atomic and conditional -> Accepted : Core invariant preserved (211 ms). One statement per account, no prior read, the business rule lives in the WHERE
4. SERIALIZABLE + retry -> Rejected: Core invariant preserved but ~50% failures. ~184× slower, and ~5 % of transfers failed for good even at low contention
5. Optimistic locking (version) -> Rejected: Core invariant preserved but ~44% failures under high contention. Could be an option for time consuming operations.
6. Pessimistic Unordered -> Rejected: Core invariant preserved but deadlocks between transfers. ~290 deadlocks per run, ~545× slower under high contention

## Decision
- Transfers use a single conditional update per account executed in ascending account id order (AtomicTransfer), in READ COMMITTED isolation level.
- The atomic strategy is pessimistic, since it locks the row and that's why the order is important to avoid deadlocks.
- The READ COMMITTED + SELECT...FOR UPDATE strategy is accepted as fallback when the balance must be read before writing.
- The CHECK (balance_minor >= 0) has to be implemented in the database, to enforce the core invariants. It caught a real bug during the measurements
- Transfers failing with 40P01 or 40001 are retried up to 3 times, which requires an idempotency key on the transfer API, otherwise a retried transfer could be executed twice.


## Consequences and trade offs
- Core invariants and business rules are preserved.
- No deadlocks between transfers
- No lost updates
____
- Transfers on the same account are serialized: a hot account’s throughput is capped at roughly 1 / lock duration.
- Locks can never be acquired in another way anywhere in the code base. All account locks go through a single repository method that sorts the ids; no FOR UPDATE elsewhere.
- Measurements were run on a single machine with 16 workers and uniformly distributed load. The numbers are relative, not absolute

## When to choose another option
- A transfer must call another service (e.g. an anti-money-laundering (AML) check) -> move the call out of the transaction or consider optimistic locking
- Accounts are spread across multiple shards -> consider a saga or ledger
- Any 40P01 in production → someone broke the lock-order rule.
- A single account exceeds N transfers/s, or p99 lock wait on an account exceeds X ms → append-only ledger or sub-accounts. To be callibrated by load tests
