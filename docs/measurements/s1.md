`transactions` is the slowest per row: each insert checks two foreign keys (`from_account_id`, `to_account_id`).

Index breakdown (at this stage, only primary keys and the unique constraint):

Query used:

```sql
SELECT relname,
       pg_size_pretty(pg_relation_size(relid))       AS table_size,
       pg_size_pretty(pg_indexes_size(relid))        AS indexes_size,
       pg_size_pretty(pg_total_relation_size(relid)) AS total
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

```sql
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'table_name';
```

### Observations

- A transaction takes ~85 bytes in the table, of which ~24 bytes are the row header (including `xmin`/`xmax`): that is the cost of MVCC.
- The unique index on `email` (`text`) is 3 times the size of the `users` primary key index (`bigint`): index size depends on key width.
- Foreign keys are not indexed yet (Tuesday's topic): bytes per row will go up.

### Extrapolation to 65 M users

**Tables that scale with the number of users** (rule of three on the total):

| Table | 1 M users | 65 M users |
| --- | ---: | ---: |
| `users` | 178 MB | ~11.5 GB |
| `accounts` | 113 MB | ~7 GB |

**`transactions` grows with time, not with the number of users.** Basis: ~107 bytes per transaction (table + primary key).

| Assumption | Transactions | Size |
| --- | ---: | ---: |
| A1 — stock: 5 transactions per user in total | 325 M | ~33 GB |
| A2 — flow: 10 transactions per user per month | 650 M / month | ~66 GB / month, **~800 GB / year** |

A1 is a snapshot and underestimates the problem. A2 is the right reasoning: volume depends on activity and retention period.

### Takeaway for question 1

The user-bound tables fit in ~20 GB: 65 M users is not the problem. The real issue is transactions: ~0.8 TB per year before secondary indexes, so several TB after a few years. That is where date partitioning (Thursday), archiving and retention come in.

## Tuesday 6 — Account history

### Method

- Indexes: `db/03-index.sql`

  ```sql
  CREATE INDEX idx_tx_from_created  ON transactions (from_account_id, created_at);
  CREATE INDEX idx_tx_to_created    ON transactions (to_account_id,   created_at);
  CREATE INDEX idx_accounts_user ON accounts (user_id);
  ```

- `EXPLAIN (ANALYZE, BUFFERS)`, each query run 3 times, **last run kept** (warm cache). Times are the server-side `Execution Time`.
- "No index" measurements were taken with the indexes in place but disabled for the session (`SET enable_indexscan = off; SET enable_bitmapscan = off;`).
- Hot account: **42** (1,370 transactions). Quiet account: **900000** (6 transactions).
- Buffers are 8 kB pages. `hit` = found in PostgreSQL's shared buffers; `read` = requested from the OS (OS page cache or disk).

### Queries

**A. Account history, `OR` version**

```sql
SELECT *
FROM transactions
WHERE from_account_id = 42 OR to_account_id = 42
ORDER BY created_at DESC
LIMIT 50;
```

**B. Account history, `UNION ALL` version**: each branch reads the 50 most recent rows straight from its index.

```sql
SELECT * FROM (
    (SELECT * FROM transactions WHERE from_account_id = 42
     ORDER BY created_at DESC LIMIT 50)
    UNION ALL
    (SELECT * FROM transactions WHERE to_account_id = 42
     ORDER BY created_at DESC LIMIT 50)
) AS t
ORDER BY created_at DESC
LIMIT 50;
```

**C. A user's outgoing transactions** (join through an unindexed foreign key)

```sql
SELECT t.*
FROM accounts a
JOIN transactions t ON t.from_account_id = a.id
WHERE a.user_id = 123456
ORDER BY t.created_at DESC
LIMIT 50;
```

### Results

| # | Query | Account | Main nodes | Execution time | Buffers |
| --- | --- | --- | --- | ---: | ---: |
| 1 | A `OR`, no index | 42 | Parallel Seq Scan + top-N sort | 143.6 ms | 51,621 |
| 2 | A `OR`, no index | 900000 | Parallel Seq Scan + sort | 217.9 ms | 51,621 |
| 3 | A `OR`, indexes | 42 | BitmapOr + Bitmap Heap Scan + top-N sort | 11.7 ms | 1,356 |
| 4 | A `OR`, indexes | 900000 | BitmapOr + Bitmap Heap Scan + sort | 0.24 ms | 12 |
| 5 | B `UNION ALL`, indexes | 42 | Merge Append + 2 × Index Scan Backward | 1.96 ms | 57 |
| 6 | B `UNION ALL`, indexes | 900000 | Merge Append + 2 × Index Scan Backward | 0.17 ms | 14 |
| 7 | C join, no index on `user_id` | — | Parallel Seq Scan on `accounts` | 59.9 ms | 11,224 |
| 8 | C join, index on `user_id` | — | Index Scan on `accounts` | 0.70 ms | 13 |

Hot account, from no index to the rewrite (1 → 5): **73× faster, 900× fewer pages read**.

Run-to-run variance without index (cold → warm): 437.8 / 369.2 / 143.6 ms for account 42, 366.5 / 219.6 / 217.9 ms for account 900000. Line 8 is a first run (`read=3`): the index pages were not cached yet.

### Observations

1. **Without an index, every lookup reads the whole table.** 51,621 pages × 8 kB = 403 MB, exactly the size of `transactions` measured on Monday. The hot and the quiet account cost the same: the work depends on the table size, not on the result size.
2. **The `read` count stays at ~42,500 even on the third run.** For a sequential scan of a table larger than a quarter of `shared_buffers` (403 MB > 256 MB), PostgreSQL uses a small ring buffer so that one big scan does not evict the cache. The speed-up from 438 to 144 ms comes from the OS page cache, not from PostgreSQL's.
3. **The `OR` with indexes still reads the whole history of the account.** 1,370 rows are fetched to keep 50, and `Heap Blocks: exact=1345` means almost one page per row: an account's transactions are scattered across the table because they were inserted over time. A top-N sort follows.
4. **The `UNION ALL` reads only what it returns.** Each branch walks its index backwards and stops after 50 entries; no sort is needed because the index is already ordered by `created_at` within an account. 57 pages instead of 1,356 (24× fewer), 1.96 ms instead of 11.7 ms (6× faster).
5. **An ascending index serves a descending query.** The indexes are on `created_at` ascending and the plan shows `Index Scan Backward`: a B-tree can be read in both directions, so `DESC` in the index definition is not needed here.
6. **On a quiet account, both versions are equivalent** (0.24 ms and 12 pages vs 0.17 ms and 14 pages). The rewrite only pays off for accounts with a long history, which are precisely the ones that hurt in production.
7. **Unindexed foreign keys are a classic trap.** PostgreSQL indexes primary keys automatically, but not foreign keys. Finding the accounts of one user read the whole `accounts` table: 11,224 pages ≈ 88 MB, its size measured on Monday. With the index: 13 pages, 85× faster.

### Additional experiment: full history without `ORDER BY` / `LIMIT`

Same `OR` and `UNION ALL` queries, returning all the rows of the account. Single run each, so these numbers are indicative only.

| Version | Account | No index | With indexes |
| --- | --- | ---: | ---: |
| `OR` | 42 | 315.0 ms (1 Parallel Seq Scan) | 35.3 ms (1,356 buffers) |
| `UNION ALL` | 900000 | 402.9 ms (2 Parallel Seq Scans) | 1.6 ms (12 buffers) |

**Finding:** without an index, `UNION ALL` is slower than `OR`, because it scans the table twice (once per branch) instead of once. The rewrite is only worth it when each branch can use an index.

Note: the two versions were run on different accounts. For a sequential scan this does not matter (the whole table is read anyway); with indexes the numbers are not comparable.

Client-side timings from pgAdmin ("Query complete", 0.06 to 0.93 s) were discarded: they include network and rendering, pgAdmin stops at 1,000 rows, and they varied by a factor of 5 for the same query.

### Takeaway for question 1

Before scaling anything, find the queries that read far more than they return (`pg_stat_statements`, then `EXPLAIN (ANALYZE, BUFFERS)`). On 5 M transactions, an account history without an index read the whole 400 MB table to return 50 rows; a composite index `(account_id, created_at)` plus a `UNION ALL` rewrite brought it to 57 pages and 2 ms. Unindexed foreign keys are the other quick win. At 65 M users, this is the difference between reading pages and reading the table, and the `OR` itself disappears with a double-entry ledger (one row per account and movement, one index).

### Observations

1. **A partial index stores only the rows you query.** Indexing `status` alone would be almost useless (3 values for 5 M rows), but the rare value is exactly the one the retry job needs. The partial index is 65× smaller than a full one, so it is cheap to maintain and stays in memory.
2. **A covering index removes table access, not time, as long as everything is cached.** 53 → 22 pages, but 0.25 ms vs 0.39 ms, which is sub-millisecond noise. Each page saved is one random read avoided when the table no longer fits in memory: the gain grows with the data, the cost does too.
3. **An Index Only Scan needs an up-to-date visibility map.** Right after `VACUUM FULL`, the plan said `Index Only Scan` but did 50 heap fetches (one per row) and read 56 pages, worse than the plain index. `VACUUM FULL` rewrites the table but does not set the visibility map; a plain `VACUUM` does. On a busy table, autovacuum settings directly affect read performance.
4. **22 pages for 50 index entries is more than expected** (~4: 3 levels + 1 leaf). Likely explanation, not verified: the visibility map of a 51,621-page table spans 2 pages, the rows of account 42 are scattered across both halves of the table, and each switch between the 2 map pages counts as a buffer hit.
5. **`INCLUDE` is not free.** The covering index is 278 MB vs 150 MB for the same key without included columns (+85 %). Indexes now weigh more than the table itself.
6. **Every insert also pays for foreign keys.** `pg_stat_statements` showed 14.7 M calls (43 s in total) to `SELECT … FROM accounts … FOR KEY SHARE`: two foreign-key checks per inserted transaction (5 M seed + 2.3 M pgbench rows, × 2).
7. **A write benchmark changes the data it measures.** The four pgbench runs inserted 2,333,965 rows (5 M → 7.3 M). They were deleted (`created_at >= '2026-10-06'`) and the table rebuilt with `VACUUM FULL` to keep the 5 M baseline for the next measurements.
8. **`pg_stat_statements` must be filtered before it is read.** The first top 10 was the seed, `CREATE INDEX` and the benchmark; after `pg_stat_statements_reset()`, pgAdmin's catalog queries came first. The real application queries were all fast: 2.33 ms for the retry job (D), 1.95 ms for a user's outgoing transactions (C). Two views matter: total time (frequent, cheap queries) and mean time (rare, slow ones).

### Takeaway for question 1

Indexes are a trade-off, not a default. A partial index turns a 1-second job into 0.3 ms for 1.6 MB; a covering index removes table access for the hottest read; but the three secondary indexes already cost ~16 % of insert throughput and weigh more than the table. On a write-heavy table like `transactions` at 65 M users, every index must match a measured query, and covering indexes only pay off if vacuum keeps the visibility map current.

## Thursday 8 — Monthly partitioning

### Method

- Partitioned copy of `transactions` (`db/04-partition.sql`): `transactions_p`, `PARTITION BY RANGE (created_at)`, **26 monthly partitions** (October 2024 → November 2026), primary key `(id, created_at)`. On every partition, the same two account indexes as on Tuesday (not Wednesday's covering index):

  ```sql
  CREATE INDEX ON transactions_p (from_account_id, created_at DESC);
  CREATE INDEX ON transactions_p (to_account_id, created_at DESC);
  ```

- Same 5 M rows in both tables (`INSERT INTO transactions_p SELECT * FROM transactions`, then `ANALYZE`). Data: 403 MB in both cases; indexes: 505 MB (partitioned) vs 537 MB (plain). A full month is ~208,000 rows and 17 MB.
- `EXPLAIN (ANALYZE, BUFFERS)`, each query run twice, **second run kept** (warm cache) unless stated otherwise. JIT disabled (`SET jit = off`) for the period query: on a first run it took 62 ms out of 282.
- Plain-table baseline for the account history: Tuesday's lines 5 and 6 (same index shape).
- Archiving: the `DELETE` is measured with `EXPLAIN ANALYZE` and the `DETACH` with psql `\timing`, both inside a transaction that is rolled back.

### Queries

**F. Daily volume of last month** (September 2026)

```sql
SELECT date_trunc('day', created_at) AS day, count(*), sum(amount_minor)
FROM transactions_p          -- or transactions
WHERE created_at >= date_trunc('month', now()) - interval '1 month'
  AND created_at <  date_trunc('month', now())
GROUP BY 1
ORDER BY 1;
```

**G. Account history**: query B (`UNION ALL`) from Tuesday, with **both** branches on `transactions_p`.

**G'. Account history limited to the last 12 months**: query G with a date bound in each branch, so that pruning applies.

```sql
(SELECT * FROM transactions_p
 WHERE from_account_id = 900000 AND created_at >= now() - interval '1 year'
 ORDER BY created_at DESC LIMIT 50)
-- same bound in the to_account_id branch
```

**H. Archiving everything older than 18 months**

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM transactions WHERE created_at < now() - interval '18 months';
ROLLBACK;

BEGIN;
ALTER TABLE transactions_p DETACH PARTITION transactions_p_2024_10;
-- … same for 2024_11, 2024_12, 2025_01, 2025_02, 2025_03
SELECT count(*) FROM transactions_p;
ROLLBACK;
```

### Results

**What partitioning speeds up: queries on a time range (F)**

| # | Table | Main nodes | Planning time | Execution time | Buffers |
| --- | --- | --- | ---: | ---: | ---: |
| 14 | `transactions` | Parallel Seq Scan (2 workers) + sort | 1.06 ms | 705.7 ms | 51,621 |
| 15 | `transactions_p` | 1 Seq Scan (`Subplans Removed: 25`) + sort | 2.0 ms | 159.6 ms | 2,145 |

**24× fewer pages, 4.4× faster, with 1 process instead of 3.**

Copying the 5 M rows into the partitioned table took 18.7 s (pgAdmin timing, indicative).

### Observations

1. **Pruning happened at execution time.** `Subplans Removed: 25` means the planner kept all 26 partitions and the executor dropped 25 at startup: the bounds use `now()`, which is not a constant at planning time. With literal dates, the pruned partitions would not appear in the plan at all.
2. **Pages fall much more than time when everything is cached.** 24× fewer pages but 4.4× faster: with no disk reads, the cost is CPU, and the sort and aggregation of the 208,000 rows of September are the same on both tables. On data that does not fit in memory, every page not read is a disk read saved. The plain table also needed 3 processes, which a busy server would take away from other queries.
3. **An ordered Append stops as soon as the `LIMIT` is reached.** Partitions are scanned newest first. For the active account, the `from` branch found its 50 rows in October and September 2026: only 3 partition indexes were scanned, the other 23 are `never executed`.
4. **The quiet account is the worst case.** It never reaches 50 rows, so all 26 × 2 partition indexes are probed, ~3 pages each: 158 pages instead of 14. Partitioning penalises accounts with **little** activity, and the cost grows with the number of partitions, not with the data volume.
5. **Cold vs warm shows where the risk is.** The same 158 pages took 21 ms from disk and 0.71 ms from cache. The page count is the stable metric; at 65 M users, where the data does not fit in RAM, it turns into random reads.
6. **`Merge Append` reads its branches on demand.** For account 42, the `to` branch stopped after its first row (July 2026): it was older than the 50 rows already supplied by the `from` branch.
7. **Partitioning adds a fixed planning cost.** About 2 ms per query with 26 partitions, versus ~1 ms on the plain table. The first query after the `DETACH` / `ROLLBACK` took 19.8 ms to plan; likely explanation, not verified: the partition descriptions had to be reloaded into the cache. This cost grows with the number of partitions, one reason not to partition by day.
8. **`DELETE` touches rows, `DETACH` touches the catalog.** The `DELETE` read the whole table (1.9 s of sequential scan), then wrote an `xmax` on 1.27 M rows: after a `COMMIT`, they would be dead tuples (bloat, a `VACUUM` to pay on the table and its indexes, WAL for every row). The `DETACH` only turns a partition into a standalone table, which can then be exported to cold storage and dropped: ~14 ms whatever the partition size.
9. **Retention must follow partition bounds.** The cut-off was 8 April 2025: the `DETACH` archived 51,119 fewer rows than the `DELETE`, because 1–8 April 2025 sits in the April partition, which is still partly inside the window. In production, retention is defined in whole months.
10. **A plain `DETACH` takes an `ACCESS EXCLUSIVE` lock on the parent** until the end of the transaction (from the documentation, not measured here). In production: `DETACH PARTITION … CONCURRENTLY`, which does not block reads and writes but cannot run inside a transaction block.
11. **Check that every node of the plan reads the expected table.** The first history measurement had the second `UNION ALL` branch still on `transactions`: the plan mixed both tables (`Index Scan Backward using idx_tx_to_created on transactions`). It was discarded and measured again.

12. **A date bound helps exactly the accounts that partitioning hurts.** With 12 months, 12 of the 26 partitions are pruned in each branch, and the quiet account's pages drop in proportion to the partitions kept (28 / 52 × 158 ≈ 85; measured: 81). The active account gains nothing: the pruned partitions were already `never executed`. A shorter window (e.g. 3 months) would bring the quiet account close to the plain table; not measured.
13. **A date bound changes the result.** Account 900000 returns 1 row instead of 6: the other 5 are older than a year. Bounding the history is a product decision, not a transparent optimisation: the screen shows "last 12 months", and "load more" queries the previous window with a cursor on `created_at`.
14. **Planning time is noisy at this scale.** Between 1.9 and 7.1 ms across runs of the same query, all buffers in cache. Planning differences of a few milliseconds are not meaningful here without more runs.

### Takeaway for question 1

At 65 M users, `transactions` grows by ~66 GB a month, so the question is how to live with the flow, not how to store the stock. Monthly partitioning makes the two big operations on time cheap: a month of reporting reads 24× fewer pages, and archiving 18 months goes from a 3.1-second `DELETE` that leaves 1.27 M dead tuples to an 85 ms `DETACH`. The price is paid on per-account reads: a quiet account probes every partition (158 pages instead of 14), plus a planning cost that grows with the number of partitions. The fix is to bound the account history by date and paginate with a cursor on `created_at`, so that pruning applies: with a 12-month window, the quiet account already reads half the pages (81 instead of 158). This is preferable to partitioning by account hash, which would bring archiving back to `DELETE`.
