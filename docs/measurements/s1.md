`transactions` is the slowest per row: each insert checks two foreign keys (`from_account_id`, `to_account_id`).

### Volume

Checked with `count(*)`: 1,000,000 users, 1,200,000 accounts, 5,000,000 transactions.

| Table | Table | Indexes | Total | Bytes/row (total) |
| --- | ---: | ---: | ---: | ---: |
| `transactions` | 403 MB | 107 MB | 510 MB | ~107 |
| `users` | 89 MB | 89 MB | 178 MB | ~187 |
| `accounts` | 88 MB | 26 MB | 113 MB | ~99 |

Index breakdown (at this stage, only primary keys and the unique constraint):

| Index | Size |
| --- | ---: |
| `transactions_pkey` | 107 MB |
| `users_email_key` | 68 MB |
| `accounts_pkey` | 26 MB |
| `users_pkey` | 21 MB |

Query used:

```sql
SELECT relname,
       pg_size_pretty(pg_relation_size(relid))       AS table_size,
       pg_size_pretty(pg_indexes_size(relid))        AS indexes_size,
       pg_size_pretty(pg_total_relation_size(relid)) AS total
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

### Observations

- A transaction takes ~85 bytes in the table, of which ~24 bytes are the row header (including `xmin`/`xmax`): that is the cost of MVCC.
- The unique index on `email` (`text`) is 3 times the size of the `users` primary key index (`bigint`): index size depends on key width.
- Foreign keys are not indexed yet (Tuesday's topic): bytes per row will go up.

### Extrapolation to 65 M users

**Tables that scale with the number of users** (rule of three on the total):

| Table | 1 M users | 65 M users |
| --- | ---: | ---: |
| `users` | 178 MB | ~11.5 GB |
| `accounts` | 113 MB | ~7 GB |

**`transactions` grows with time, not with the number of users.** Basis: ~107 bytes per transaction (table + primary key).

| Assumption | Transactions | Size |
| --- | ---: | ---: |
| A1 — stock: 5 transactions per user in total | 325 M | ~33 GB |
| A2 — flow: 10 transactions per user per month | 650 M / month | ~66 GB / month, **~800 GB / year** |

A1 is a snapshot and underestimates the problem. A2 is the right reasoning: volume depends on activity and retention period.

### Takeaway for question 1

The user-bound tables fit in ~20 GB: 65 M users is not the problem. The real issue is transactions: ~0.8 TB per year before secondary indexes, so several TB after a few years. That is where date partitioning (Thursday), archiving and retention come in.
